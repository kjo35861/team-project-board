# 2단계 기술 구성 및 저장 방식 선택안

> `roadmap.md` 2단계 산출물입니다. 1단계의 제품 요구사항은 `mvp-scope.md`를 따릅니다. 아래는 현재 정적 HTML/CSS 시안과 MVP 범위에 맞춘 구현 기준안입니다. 기술 방향을 정리한 문서이며, 외부 서비스 계정 생성·프로젝트 설정·배포·기능 구현·테스트는 아직 진행하지 않았습니다. 다른 기술 선호가 생기면 구현 전에 이 문서를 바꿀 수 있습니다.

## 1. 기술 선택 요약

| 영역 | 선택안 | 역할 |
|---|---|---|
| 프런트엔드 | Vite + 프레임워크 없는 JavaScript ES 모듈 | 현재 `index.html`과 `styles.css`를 재사용하고 화면 동작을 추가합니다. |
| 패키지·개발 서버 | Node.js LTS + npm | 의존성 관리, 로컬 개발 서버와 빌드를 제공합니다. |
| 인증 | Supabase Auth | 이메일·비밀번호 가입, 로그인, 이메일 확인과 세션을 관리합니다. |
| API·서버 | `@supabase/supabase-js`와 Supabase Data API, 필요한 DB RPC | 일반 요청은 인증된 클라이언트에서 보내고, 권한이 중요하거나 원자성이 필요한 작업은 DB 함수로 처리합니다. 별도의 맞춤형 REST 서버는 두지 않습니다. |
| 데이터베이스 | Supabase PostgreSQL + Row Level Security(RLS) | 모든 보드·업무의 공유 원본입니다. 화면에서 버튼을 숨기는 것만으로 권한을 보호하지 않습니다. |
| 파일 저장 | MVP에서 사용하지 않음 | 파일 첨부가 범위에 없으므로 Supabase Storage도 도입하지 않습니다. |
| 호스팅 | Vercel 정적 사이트 배포 | Vite 빌드 결과물(`dist`)을 배포합니다. 미리보기와 운영은 서로 다른 Supabase 프로젝트를 사용합니다. |
| 스키마·테스트 | Supabase CLI 마이그레이션, Vitest | DB 변경 이력을 SQL로 관리하고, 순수 검증·날짜·필터 로직을 자동 테스트합니다. |

## 2. 구성 요소와 데이터 흐름

```text
브라우저 (기존 HTML/CSS + Vite로 빌드한 JavaScript)
  ├─ 이메일 로그인·인증 ───────────────> Supabase Auth
  └─ 업무·보드 요청 (HTTPS, 사용자 세션) ─> Supabase Data API ─> PostgreSQL + RLS
                                             └─ 권한·원자성이 필요한 작업 ─> DB RPC

Vercel은 정적 화면 파일을 제공하고, 업무 데이터의 원본은 Supabase PostgreSQL에 둡니다.
```

- 보드에 들어갈 때 서버에서 해당 보드의 최신 업무를 가져오고, 생성·수정·삭제 성공 뒤에는 화면 데이터를 갱신합니다. 보드 화면으로 다시 돌아올 때도 최신 데이터를 다시 확인합니다.
- **MVP 첫 구현에는 상시 실시간 푸시 동기화를 넣지 않습니다.** 현재 요구사항은 팀원이 같은 서버 데이터를 공유하는 것이며, 자동 실시간 갱신은 별도 요구로 확정되지 않았습니다. 따라서 다른 팀원의 변경은 화면 재조회 시 반영됩니다. 실제 사용에서 필요성이 확인되면 Supabase Realtime을 후속으로 추가할 수 있습니다.
- 브라우저는 인증된 사용자의 세션으로 요청합니다. DB는 각 요청에서 보드 소속과 역할을 검사하므로, URL이나 클라이언트 코드가 바뀌어도 권한 없는 보드 데이터를 읽거나 변경할 수 없어야 합니다.
- 보드 초대 수락처럼 여러 DB 변경을 한 번에 처리해야 하는 흐름은 트랜잭션으로 실행되는 RPC를 사용합니다. `SECURITY DEFINER`를 쓰는 함수는 `auth.uid()` 확인, 고정 `search_path`, 최소 실행 권한과 권한 검증을 갖추고 테스트합니다.

## 3. 저장 및 권한 기준

- **최종 공유 데이터의 원본은 PostgreSQL**입니다. 업무와 보드 데이터를 브라우저 `localStorage`에 저장해 협업 데이터를 대신하지 않습니다. 인증 세션은 Supabase Auth 클라이언트가 관리합니다.
- 현재 첫 기능 구현은 도구만으로 실행 환경과 외부 서비스 설정을 준비할 수 없어 브라우저 `localStorage`를 사용하는 로컬 프로토타입입니다. 이 저장은 같은 브라우저에만 적용되며, 팀 공유·접근 권한·백업을 제공하지 않습니다. 실제 공유 저장을 구현하면 이 임시 저장을 데이터 원본으로 사용하지 않습니다.
- 4단계에서 확정할 논리 테이블 후보는 `profiles`, `boards`, `board_members`, `tasks`, `board_invites`입니다. 실제 필드·제약 조건·인덱스·삭제 규칙은 데이터 모델 설계에서 정합니다.
- 앱에서 사용하는 모든 공개 스키마 테이블에 RLS를 켜고, 기본은 접근 거부로 둡니다. 보드 구성원만 해당 보드를 읽고 업무를 다룰 수 있으며, 소유자와 팀원의 삭제·초대·보드 관리 차이는 `mvp-scope.md` 규칙을 DB/API에서 강제합니다.
- 담당자는 같은 보드의 참여자여야 하며, 업무 제목 길이와 상태 값 같은 검증도 클라이언트 안내에만 의존하지 않고 데이터베이스 제약 또는 서버 측 검증으로 보강합니다.
- 초대 링크는 소유자만 발급·취소하고 7일 동안 한 번만 수락할 수 있어야 합니다. 원문 토큰은 안전한 난수로 만들고 DB에는 해시만 보관하며, 만료·취소·중복 수락을 서버에서 원자적으로 검사합니다. 초대 이메일 발송은 MVP 범위에 없으므로 링크를 앱에서 만들어 팀원에게 별도로 전달합니다.
- 스키마와 RLS 정책은 `supabase/migrations/`의 버전 관리되는 SQL 마이그레이션으로 관리합니다. 실제 스키마는 4단계에서 설계하고, 구현은 5단계 기반 설정 이후 진행합니다.

## 4. 환경과 비밀값 관리

### 환경 분리

1. **로컬 개발·DB 검증:** Vite 개발 서버와 Supabase CLI의 로컬 환경을 사용합니다. 로컬 Supabase 실행에는 Docker가 필요합니다.
2. **개발·미리보기:** 개발용 Supabase 프로젝트와 Vercel Preview를 연결합니다. 테스트용 데이터만 사용합니다.
3. **운영:** 별도 운영 Supabase 프로젝트와 Vercel Production을 연결합니다. 개발 데이터와 운영 데이터는 섞지 않습니다.

DB 마이그레이션은 로컬에서 먼저 확인하고 개발 환경에 적용한 뒤, 검증이 끝난 변경만 운영에 적용합니다. 각 환경의 인증 콜백·허용 URL도 해당 환경 도메인으로 제한합니다.

### 브라우저 설정값과 비밀값

- 브라우저 앱에는 Supabase 프로젝트 URL과 **공개용 publishable/anon 키**만 설정합니다. 예를 들면 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLIC_KEY`를 사용할 수 있습니다.
- Vite에서 `VITE_` 접두사가 붙은 값은 빌드 결과에 포함될 수 있습니다. 그러므로 비밀번호, SMTP 자격 증명, `service_role` 키 등 비밀값을 이 변수에 넣지 않습니다. 공개 키는 그 자체로 접근 권한을 부여하지 않으며, RLS가 올바르게 적용되어야 합니다.
- 로컬 값은 이후 구현 단계에서 Git 제외 대상인 `.env.local`에 두고, 배포 값은 Vercel 환경 변수와 Supabase의 해당 서비스 설정에 등록합니다. 실제 키를 소스 코드나 저장소에 커밋하지 않습니다. 이 문서 작성 과정에서 키나 계정 정보는 만들거나 수집하지 않았습니다.
- Supabase Auth 이메일 확인은 MVP에 포함됩니다. 운영 출시 전에는 확인 메일의 안정적인 발송을 위해 SMTP/발신 도메인과 각 환경의 리디렉션 URL을 설정해야 합니다. 앱에서 초대 이메일을 보내는 기능은 구현하지 않습니다.

## 5. 구현 및 검증 방향

- 로드맵 5단계에서 `package.json`, Vite 설정, Supabase 클라이언트 초기화와 환경 변수 예시를 추가합니다. 기존 HTML/CSS 레이아웃은 가능한 한 유지하고, 이벤트·화면 렌더링·데이터 요청은 ES 모듈로 분리합니다.
- Vitest로 제목 검증, 필터·정렬, `Asia/Seoul` 기준 마감일 계산처럼 화면 밖에서도 확인할 수 있는 로직을 검증합니다.
- Supabase 로컬 환경에서는 SQL 제약, RPC와 RLS를 소유자·팀원·비구성원 계정으로 확인합니다. 특히 비구성원의 읽기·쓰기 거부, 업무 담당자 소속, 팀원 삭제 권한, 만료·재사용된 초대 링크를 확인합니다.
- 브라우저의 데스크톱·모바일 화면과 이메일 확인 흐름은 기능이 구현된 뒤 별도로 확인합니다. **이 문서 작성과 이번 로컬 기능 구현 중 자동 테스트나 브라우저 테스트를 실행하지 않았습니다.**

## 6. 선택 이유와 한계

### 선택 이유

- 현재 시안이 이미 HTML/CSS로 구성되어 있어 프레임워크 전환 없이 화면을 기능화할 수 있습니다.
- Supabase는 이메일 인증, 관계형 DB, API와 DB 수준 권한을 한 구성으로 제공하므로, 공유 데이터와 보드별 접근 제어에 잘 맞습니다.
- 별도 서버를 처음부터 운영하는 것보다 MVP의 배포·운영 구성이 단순합니다. Vercel은 프런트엔드 정적 배포를 담당하고 Supabase는 인증과 데이터를 담당합니다.

### 알고 있어야 할 한계

- 이 방식은 Supabase와 Vercel에 의존합니다. 다른 서비스로 옮길 때 인증·API·DB 구성을 바꾸어야 할 수 있습니다.
- RLS와 DB 함수는 보안 경계이므로 단순 UI 테스트만으로 완료 처리할 수 없습니다. 권한 조합별 DB 테스트가 필요합니다.
- MVP 첫 버전은 자동 실시간 갱신을 보장하지 않습니다. 다른 팀원의 변경은 다시 불러올 때 나타나며, 실시간성이 요구되면 별도 범위와 검증을 추가합니다.
- 운영용 인증 메일 발송, 도메인, 각 서비스 계정 및 배포 설정은 구현·출시 단계에서 준비해야 합니다. 현재 서비스 요금이나 계정의 무료 한도는 확인하거나 확정하지 않았습니다.
- 현재 앱 기능은 브라우저 로컬 저장을 이용하는 프로토타입입니다. 이 저장은 공유 가능한 데이터 원본, 사용자 인증 또는 백업이 아니며 보안 경계로 사용하면 안 됩니다.

## 7. 단계 상태

**기술 방향 선택안 작성 완료:** 프런트엔드, 인증·API·DB, 권한 적용 위치, 공유 데이터 원본, 환경 분리, 배포 방식과 비밀값 관리 방향을 정리했습니다.

**초기 로컬 UI 구현:** 기존 HTML/CSS에 업무 입력·수정·삭제, 검색·필터·정렬 등 브라우저 기능을 추가했습니다. 이는 Vite·Supabase를 설치하거나 설정했다는 뜻이 아닙니다.

**아직 하지 않은 일:** `package.json` 생성, 라이브러리 설치, Supabase/Vercel 프로젝트 생성, DB 마이그레이션, 키 등록, 서버 기능 구현, 브라우저 테스트, 배포. 실제 로그인이나 팀 공유 저장은 동작하지 않습니다.

다음은 로드맵 **4단계: 데이터 모델과 접근 권한 설계**입니다. `mvp-scope.md`의 제품 규칙과 이 문서의 Supabase/PostgreSQL 기준, `user-flow.md`의 주요 동작을 함께 반영해 테이블·관계·제약 조건·RLS 정책을 구체화합니다. 이후에도 문서 설계와 구현을 병행하며, 실행 환경이 필요한 설정이나 검증은 완료 여부를 구분해 기록합니다.
