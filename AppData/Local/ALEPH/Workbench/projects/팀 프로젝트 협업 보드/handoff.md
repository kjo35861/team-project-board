# 다른 LLM을 위한 프로젝트 인수인계

## 1. 프로젝트 개요

- **프로젝트:** 팀 프로젝트 협업 보드
- **목표:** 팀원이 업무를 등록하고 담당자·마감일·진행 상태를 공유하는 웹 앱
- **기술 방향:** Vite + 바닐라 JavaScript, Supabase Auth/PostgreSQL/RLS, Vitest
- **현재 앱 실행 진입점:** `index.html` → `/src/main.js`; `src/main.js`가 인증 후 기존 화면인 `app.js`를 불러옵니다.
- `index.html`을 `file://`로 직접 열지 말고 `npm run dev`로 실행해야 합니다.

## 2. 현재 위치 — 코드 작성 기준

현재 작업 위치는 **3.3 업무 생성 저장소 구현까지**입니다. 다음 세부 작업은 **3.4 업무 수정·상태 변경 저장소**입니다.

### 구현 코드가 있는 범위

- **1번 파트 로컬 보드 프로토타입:** 업무·보드 CRUD, 상태 변경, 검색·필터·정렬 및 `localStorage` 저장이 `app.js`에 있습니다.
- **인증 및 서버 보드 기능:** Supabase 인증과 공유 보드·구성원·초대 저장소/UI 코드가 `src/`에 있습니다. 진행 문서상 2.25~2.29까지 코드 반영됨.
- **2.1~2.20:** DB 스키마·제약, RLS·권한, RPC 마이그레이션과 pgTAP 테스트 파일이 작성되어 있습니다.
- **2.21~2.29:** 보드/구성원/초대 저장소와 UI 및 Vitest 테스트 코드가 작성되어 있습니다.
- **3.1:** 업무 입력 검증 `src/lib/task-validation.js`와 테스트 코드.
- **3.2:** `src/lib/task-repository.js`의 `listTasks(client, boardId)` 및 테스트 코드.
- **3.3:** 같은 저장소의 `createTask(client, boardId, input)` 및 테스트 코드.

현재 업무 저장소에는 **조회와 생성만** 있습니다. 수정·상태 변경·삭제는 아직 구현되지 않았고, 조회·생성 함수도 화면에서 호출되지 않습니다.

### 중요한 작동 한계

공유 보드·구성원·초대 UI 코드는 `src/main.js`에서 연결되는 구조지만, 현재 업무 UI는 서버 보드 선택과 연결되어 있지 않습니다. 업무는 계속 `app.js`의 사용자별 브라우저 `localStorage`에 저장되며, 담당자는 `index.html`/`app.js`의 예시 멤버 목록입니다. 따라서 **업무 공유, 서버 CRUD, 실제 roster 담당자 선택은 아직 기능적으로 완성되지 않았습니다.** 서버 보드를 선택해도 아래 로컬 업무 영역이 그 보드로 바뀌지 않는다는 안내도 앱에 표시됩니다.

## 3. 검증 상태 — 완료로 오인하지 말 것

저장소 파일과 문서를 확인한 결과, 테스트 코드는 여럿 존재하지만 다음의 **실행 결과는 확인되지 않았습니다.**

- Vitest (`npm test`), 프로덕션 빌드 (`npm run build`)
- Supabase 마이그레이션 적용, pgTAP 실행
- 실제 Supabase Auth/RPC/Data API 요청
- 브라우저 실행 및 여러 사용자 계정 간 공유·권한 검증

따라서 지금까지의 상태는 **코드·테스트 초안 작성**이며, 테스트 통과나 실제 DB 동작이 증명된 상태가 아닙니다. 이 인수인계 작성 과정에서도 명령 실행이나 브라우저 테스트는 하지 않았습니다.

`package.json`에 명령은 정의되어 있습니다.

```sh
npm install
npm run dev
npm test
npm run build
```

README는 Node.js 20 이상을 요구합니다. 파일 목록에는 Supabase 마이그레이션은 있지만 `supabase/config.toml`은 보이지 않으므로, 로컬 Supabase 테스트를 시작할 때 CLI 프로젝트 설정 유무를 확인해야 합니다. 실행 환경(예: Docker/CLI 또는 검증 가능한 프로젝트)이 준비되지 않으면 DB 검증을 완료 처리하지 마세요.

## 4. 다음 작업: 3.4 업무 수정·상태 변경 저장소

기준 문서에 따른 다음 작업은 `src/lib/task-repository.js`에 **인증된 사용자 기준의 업무 수정 저장 함수**를 추가하고 `src/lib/task-repository.test.js`에 단위 테스트 코드를 함께 작성하는 것입니다.

구현 시 지켜야 할 기준:

1. 기존 `createTask`/`listTasks`의 오류 처리, 인증 확인, 입력 검증, 반환값 정규화 패턴을 재사용합니다. 먼저 관련 파일을 읽고 구조와 API를 맞춥니다.
2. 보드 ID와 업무 ID를 검증하고, 현재 로그인 사용자를 확인한 뒤에만 DB 요청을 합니다.
3. 수정 가능한 입력은 업무 제목·설명·상태·담당자·마감일의 허용 필드로 제한합니다. `id`, `board_id`, `created_by`, `created_at`, `updated_at` 같은 서버 관리 필드는 클라이언트 입력으로 수정하지 않습니다. DB 테이블 권한과 RLS가 최종 권한 경계입니다.
4. 기존 `validateTaskInput`과 담당자 ID 검증·정규화 규칙을 검토해 일관되게 적용합니다. DB가 담당자와 보드 멤버십의 일치 여부를 강제하며, 저장소만으로 권한을 보장하는 것으로 취급하지 않습니다.
5. 보드 ID와 업무 ID 양쪽으로 범위를 지정해 다른 보드 업무를 수정하지 않도록 합니다. 응답의 보드 범위와 필드를 검증하고, 호출한 입력과 불일치하는 응답을 성공으로 반환하지 않습니다.
6. 저장 오류, 인증 누락, 권한 거부, 네트워크 오류, 유효하지 않은 입력/응답을 구분하고 원시 DB 오류·민감 정보를 노출하지 않습니다. 행을 찾지 못했거나 RLS 때문에 반환이 없는 경우를 성공으로 처리하지 않습니다.
7. 상태만 변경하는 API를 별도 둘지 전체 수정 API로 통일할지는 현재 UI 요구와 함수 구조를 확인해 결정하되, 수정 허용 필드 및 검증 규칙을 우회하지 않게 합니다.
8. 성공, 입력 오류, 미인증, 권한 거부, 네트워크 실패, 잘못된/범위 밖 응답, 관리 필드 위조 시도 등을 테스트 코드로 다룹니다. 테스트가 작성됐다는 이유로 통과했다고 쓰지 않습니다.

완료 후 실제로 실행하지 않았다면 다음 단계인 **3.5 삭제 저장소**를 코드 작업으로 이어갈 수 있습니다. 이후 순서는 대략 다음과 같습니다.

- **3.5~3.6:** 업무 삭제 저장소, 관리 필드 위조 방어 검토
- **3.7~3.18:** 기존 업무 화면을 서버 조회·생성·수정·삭제로 전환하고 로딩/빈 화면/오류/재시도, roster 담당자, 검색·필터·정렬, 중복 제출, 보드 전환·로그아웃 시 오래된 응답 폐기, 업무 localStorage 경로 제거
- **3.19~3.22:** 입력·검색·정렬, 저장소, DB RLS CRUD/담당자, 보드 전환 및 화면 통합 테스트 보강
- **최종 검증:** 기존 DB 마이그레이션·pgTAP, 전체 Vitest, 빌드, 실제 여러 계정 통합 및 접근성 확인

자세한 완료 기준은 `remaining-implementation-plan.md`와 `feature-implementation-plan.md`를 참고합니다.

## 5. 권한·제품 규칙

정책의 기준 문서는 `mvp-scope.md`입니다. 구현과 테스트에서 적어도 다음 기준을 유지합니다.

- 보드마다 소유자 1명, 소유자만 보드 관리·초대·일반 팀원 관리
- 팀원은 본인이 작성한 업무만 삭제 가능하며 소유자는 보드 내 업무 삭제 가능
- 초대는 7일 유효, 1회 수락; 원문 토큰은 저장하지 않고 해시만 저장
- 업무 담당자는 같은 보드의 구성원만 가능하며, 구성원 제거 시 담당자는 해제
- 서버 데이터 접근은 RLS/RPC를 권한의 최종 기준으로 삼음. UI 버튼 숨김은 보안 경계가 아님
- 초대 원문 토큰 및 비밀 키를 로그·장기 저장소·저장소 파일·채팅에 남기지 않음
- 브라우저 공개 변수에 `service_role`, `sb_secret_...`, DB 비밀번호를 넣지 않음
- 기존 localStorage 데이터를 서버로 자동 병합하지 않음
- MVP는 실시간 푸시를 약속하지 않음. 재조회로 최신 값을 반영

## 7. 다음 LLM을 위한 작업 지침

- 우선 `feature-implementation-status.md`, `remaining-implementation-plan.md`, `src/lib/task-repository.js`, `src/lib/task-repository.test.js`를 확인하고 3.4만 구현합니다.
- 새 코드와 테스트 코드를 함께 작성하고, 문서 상태도 실제 반영 범위에 맞게 갱신합니다. 아직 업무 UI 전환은 3.7 이후이므로 3.4 작업에서 기존 화면을 무리하게 서버 전환하지 않습니다.
- 기존 파일을 고칠 때는 먼저 파일을 읽고 정확한 현재 SHA-256을 사용해 저장합니다. 새 파일은 기존 파일을 덮지 않습니다.
- 실행 환경이 없어 명령이나 브라우저를 확인할 수 없다면 사용자에게 로컬 환경에서 실행하도록 안내하고, 실행하지 않은 검증을 통과라고 주장하지 않습니다.
